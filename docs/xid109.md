# NVIDIA Xid 109 (`CTX SWITCH TIMEOUT`) under sustained Proton load

Status: **unresolved**. This is a self-contained case file for picking the
investigation back up — including from a fresh LLM agent with no memory of
prior sessions. Everything stated here is either a direct observation on
this machine or a cited, checked upstream source; nothing is carried forward
on secondhand trust. Read this whole file before trying anything new —
several plausible-looking fixes are already ruled out below.

## Symptom

A game's process, audio and GPU submission all stay alive — the GPU reports
non-idle, the process keeps running, sound keeps playing — but drawing stops
permanently for that session. Only the clear colour is ever presented again;
no further draw calls land. `journalctl -k | grep "Xid (PCI"` shows Xid 109
at the moment it happens. Nothing short of killing the game and restarting
recovers it.

## Confirmed scope

Re-derived directly from `journalctl` on 2026-11-09 (grep `"Xid (PCI"` across
every retained boot, Aug 15 through Nov 8 — the persistent journal does not
go back further than that) rather than carried forward from memory: **19
occurrences across 8 boots, now three titles, not two.**

- **STAR WARS: Galactic Racer** (Steam appid 4078430) — Unreal Engine 5,
  Epic Online Services. 14 occurrences. Hit under Proton Experimental,
  Proton Hotfix *and* GE-Proton11-9 on different days.
- **Warhammer 40,000: Space Marine 2** (appid 2183900) — Saber's own Swarm
  engine, EasyAntiCheat, Proton Experimental. 2 occurrences
  (2026-11-07, 11:52:00 and 11:55:15).
- **Fallout 4** (Steam appid 377160, vanilla, launched directly from Steam —
  not the Fallout London/Heroic install that shares its prefix) — Bethesda's
  Creation Engine. 3 occurrences, all on 2026-10-18 at 17:42:51, 18:19:05
  and 18:47:49, roughly 35–40 minutes apart, each after
  the previous hang was killed and the game relaunched: all three share the
  identical faulting instruction pointer (`ip:14dcc9aa5`) and NVIDIA channel
  (`0x1b`), confirming the same crash point hit three times in one evening.
  **This one matters more than a third data point normally would: Fallout 4
  is DX11-only and has no DX12 option, so it goes through DXVK, not
  vkd3d-proton — a `d3d11.dll` sits directly in the game's own install
  directory (a DXVK/ENB-style override, confirmed by file inspection, not
  assumed), and the prefix's `d3d12.dll`/`d3d12core.dll` are Proton's usual
  universal install, never loaded by this executable.** See "Root cause,
  revisited" below for what this changes.

This spans three unrelated engines (Unreal 5, Saber's Swarm engine, Creation
Engine), two unrelated anti-cheat/online stacks (EOS, EasyAntiCheat) *and
one with neither*, two unrelated Direct3D-translation layers (vkd3d-proton
for the two DX12 titles, DXVK for Fallout 4's DX11), and three unrelated
Proton builds — ruling out a per-game, per-engine, per-translation-layer or
per-Proton-build cause even more strongly than the two-title picture did.
Space Marine 2's own menus render fine first, so the trigger is a specific
heavy workload partway into a session, not startup itself. One occurrence
(2026-10-07 21:18, boot `920bbe2b`) recurred within two minutes of a fresh
reboot taken specifically to clear the first one that same evening — a
reboot alone does not fix it. The most recent Galactic Racer recurrence
(2026-11-07 15:42:44) happened 35 seconds into the game on a boot that was
itself only 3 minutes old, so it is not specific to a stale session either.

All three titles are confirmed working on Windows on this same physical
hardware, which points at the Linux driver/translation stack rather than a
hardware fault — though that alone isn't conclusive.

**Titles exercised in the same window that never produced this symptom
(33 distinct titles, re-derived from the same journal scan, 2026-11-09):**
Cyberpunk 2077 and Warhammer 40,000: Rogue Trader by name (both reported
working fine as of 2026-11-09), plus Assassin's Creed Odyssey, BeamNG.drive,
BioShock Infinite, Boltgun, Borderlands 4, Broforce, Dead Cells, DOOM, Elite
Dangerous, Factorio, Far Cry 4, Hades II, Half Sword, Half-Life 2, Hardspace:
Shipbreaker, Jedi Fallen Order, Mad Max, NIMRODS, No Man's Sky, Noita,
RimWorld, RoboQuest, Schedule I, Shadow of Mordor, Spelunky 2, Sunset
Overdrive, TEKKEN 7, Teardown, The Witcher 3, Valheim, Vampire Survivors.
Cyberpunk 2077 is itself a heavy, modern DX12-capable title and has run
clean across at least five separate sessions spanning August–November,
including one launched directly after a Galactic Racer hang in the same
boot — so "heavy DX12 title under Proton" alone is not sufficient to
trigger this; whatever the real trigger is, it is narrower than that.
(Two unrelated Xid **32** events also appear in this window — Aug 15 tied
to `kwin_wayland`, Sep 26 tied to a process named `Renderer` — a different
error code, not reproduced since, and out of scope for this file.)

## Hardware and software stack

- GPU: RTX 5080 (Blackwell), `hardware/nvidia.nix`, open kernel modules
  (`open = true`).
- Driver: 595.71.05, the nixpkgs-stable pin in this repo's Nixpkgs revision
  (`nixpkgs.json`). The 595.71.05 release notes list exactly one fix (an
  unrelated Wayland suspend/resume rendering bug) — this was never silently
  fixed in the version Helix is pinned to.
- No driver branch available in this Nixpkgs pin reaches the version some
  reports attribute a fix to (620.70.06, see below) — checked directly
  against the packaged driver options, not assumed.

## Root cause: NVIDIA-acknowledged bug, not a mystery

Checked directly against NVIDIA's own tracker on 2026-11-08, not secondhand:
`NVIDIA/open-gpu-kernel-modules#1097` (GitHub) describes the identical
symptom — Xid 109 CTX SWITCH TIMEOUT on Blackwell (RTX 5090/5080/5070
Ti/5060 Ti) under Proton, confirmed by reporters across driver 595.58.03
through at least 615.78.08. NVIDIA has assigned it internal bug **6017526**.
This is a known bug to track, not something to wait on a future driver
release for without also trying the available mitigation below.

Root cause per that issue and corroborating reports (vkd3d-proton
`HansKristian-Work/vkd3d-proton#2914`, CachyOS forum): **descriptor heap
exhaustion** in vkd3d-proton's classic code path on Blackwell. This is
consistent with the native-reproduction results below: neither of the two
native workloads tried exercises live DX12 descriptor-heap allocation the
way actual gameplay does, which is why neither reproduced it.

**This cannot be the whole story: Fallout 4's occurrences (see "Confirmed
scope" above) never touch vkd3d-proton at all.** Fallout 4 is DX11-only and
runs through DXVK, confirmed by direct file inspection of this install, yet
it hit the identical Xid 109 CTX SWITCH TIMEOUT symptom three times.
Whatever the real underlying defect is, it is reachable through at least
two different Direct3D-translation layers (DXVK and vkd3d-proton), which
points toward something lower-level and more general than vkd3d-proton's
specific descriptor-heap code path — most plausibly a Blackwell GPU
scheduler/context-switch defect at the kernel-driver level that a range of
different heavy command-submission patterns can trip, of which DX12
descriptor-heap churn is only one. This matches Xid 109's own name (`CTX
SWITCH TIMEOUT` is a GPU engine-scheduling fault, not a Direct3D-API-level
one) better than a vkd3d-proton-specific explanation does. The
descriptor-heap config flag mitigating *some* reported cases (Crimson
Desert, see below) does not mean it addresses the only trigger.

### Update from upstream, 2026-11-09

Checked `NVIDIA/open-gpu-kernel-modules#1097` again for new activity since
2026-11-08 (still open, 18 comments as of this check). Two comments from
early November, on a *different* title (Crimson Desert, not one Helix owns)
but the same Xid 109 and the same hardware generation, add real information:

- **`Marukooh` (2026-11-03) did deep driver-side forensics and found the
  faults land inside server-RM's (GSP firmware's) own reserved GPU virtual
  address window** (`SPLIT_VAS_SERVER_RM_MANAGED_VA_START`/`_SIZE` in
  `gpu_vaspace.c`, confirmed against the 615.78.08 open-source driver —
  `[0x100000000, 0x11FFFFFFF]`), a region the application and vkd3d-proton
  never allocate into (confirmed via `VK_EXT_device_address_binding_report`
  across 11 captured sessions). With resource-tracking extensions enabled,
  the same fault reports as **Xid 31 MMU Fault** instead of Xid 109 — i.e.
  the GPU is reading a driver-internal address that isn't mapped, and Xid
  109 is one of at least two surface symptoms of the same underlying fault.
  This is independent, driver-internals-level evidence for "GPU
  scheduler/context fault," not an API-translation-layer bug — it directly
  supports the refinement above, from a different investigator on different
  hardware and a different game.
- **`Marukooh` (2026-11-07) followed up on NVIDIA driver 620.70.06** (built
  from CachyOS's not-yet-upstreamed PKGBUILDs, open kernel modules, RTX
  5070 Ti): more than 10 minutes of continuous underwater swimming (the
  specific scenario that previously hung within minutes) produced no Xid at
  all, with `VKD3D_CONFIG=descriptor_heap` enabled — explicitly *not* called
  confirmed-fixed yet by its own reporter, pending longer sessions and
  independent confirmation from others on the same driver. A separate
  reporter (`Wayfiding`, 2026-11-07) on driver 615.78.08 (older than
  620.70.06, newer than Helix's 595.71.05) reports the descriptor-heap flag
  avoiding the hang entirely on GE-Proton11-12 and Proton-CachyOS, but with
  a side effect of visibly deformed character/NPC meshes while the flag is
  active — a cost this repo's own Galactic Racer test did not get to
  evaluate, since that test's result was negative (still hung) regardless.
  Net effect on priorities below: 620.70.06 remains unavailable in this
  repo's Nixpkgs pin (confirmed again in this session, see "Hardware and
  software stack"), but it is now a somewhat firmer target to revisit than
  "some reports attribute a fix to it" implied — treat it as the single
  most promising still-untried lever once it becomes available, rather than
  a long shot.

## Ruled out, with evidence

Everything below was independently confirmed against the real artifact
(binary, log, release notes) — not assumed from a forum post or training
data.

**1. Native (non-Proton) Vulkan workload — did not reproduce it.**
`vkmark --present-mode immediate --run-forever` ran for a full 10 minutes
(confirmed real by its own `timeout` wrapper exiting 124, not instantly —
the first attempt that day used a bare `vkmark` with no store path and
never actually ran; see git history around 2026-11-07), with `nvidia-smi
-l 1` telemetry logging throughout. No Xid, no thermal or clock anomaly
(peaked at 57°C). One data point, not conclusive alone: vkmark's workload is
simpler and more repetitive than Unreal 5 or Saber's Swarm engine under
Proton. It shifts weight slightly toward the translation layer (Proton/
Wine/EOS/EAC) over a pure driver/GPU fault, but does not rule out that some
native workload could still trigger it.

**2. Native `fossilize_replay` of Galactic Racer's real pipeline cache —
also did not reproduce it, with caveats.** Run (via `steam-run`, since it's
a generic dynamically-linked binary NixOS cannot exec directly) against the
game's own 936 MB captured pipeline cache
(`steamapps/shadercache/4078430/fozpipelinesv6/steamapprun_pipeline_cache.3554f158047e28bf/steam_pipeline_cache.foz`)
for a full 10 minutes (confirmed real: genuine GPU utilization throughout,
`timeout` exited 124). No Xid; GPU stayed cooler than the vkmark run (49°C
vs. 57°C peak), consistent with pipeline-compilation-bound work rather than
sustained rendering. Two caveats keep this from being a clean "native"
result: the replayed pipelines were originally captured from a **Proton/
vkd3d session** (`engineName: vkd3d`, `applicationName:
EOSOverlayRenderer-Win64-Shipping.exe`), so this is native *execution* of
Proton-originated data, not Proton-untouched data; and several blobs failed
to parse (`Failed to parse pNext chain for sType: 1000574000`, an
unrecognized extension struct) and were silently skipped, so this did not
exercise 100% of the cache.

These two native attempts agree with each other, which is worth more than
either alone, but neither is a clean "proven not native" result given their
caveats (a simpler synthetic workload; a partial replay of Proton-originated
data). The remaining native candidate — a from-scratch native Vulkan/DX12
title with zero Proton involvement at any point — has not been tried.

**3. `VKD3D_CONFIG=descriptor_heap %command%` on Galactic Racer — did not
prevent it, and this was confirmed to be a real test, not a silent no-op.**
Tried 2026-11-08 under Proton Hotfix (verified from the actual `ps aux`
process tree at the time — not Proton Experimental as a first draft of this
note said). Hit the identical Xid 109 again at 10:42:06, about 1 minute
into the session, visually confirmed live (audio kept playing, screen went
to the clear colour).

This attempt also produced the first GPU telemetry trace leading into an
actual hang (`nvidia-smi -l 1`, logged throughout via a persistent journal
watch): utilization was low and bursty (7–40%) for the preceding ~50
seconds, then at 10:42:03 — 3 seconds before the Xid — utilization jumped to
and pegged at 100%, clocks locked at max boost (2917 MHz), while power draw
stayed at only 48–60 W, far below what genuine 100%-utilization work on this
card draws (200–300 W+). High reported utilization with anomalously low
power is consistent with the GPU spinning on an already-wedged context
switch for a few seconds before the driver's watchdog gives up and logs the
Xid, rather than a sudden failure with no warning.

Confirming this was a real test mattered because the obvious fix
(`HansKristian-Work/vkd3d-proton#2805`) turned out to be a closed,
never-merged "bringup" prototype — so it had to be checked whether
descriptor-heap support existed in the actually-bundled vkd3d-proton at all.
It does: descriptor-heap support was later productized through many
subsequent phases and genuinely merged as `#3046` ("Descriptor heap - Phase
15/16", merged 2026-05-27). The vkd3d-proton bundled in this Proton Hotfix
build is commit `2230755878b0` (2026-10-06, well after that merge) — read
directly from `files/lib/wine/vkd3d-proton/version` inside the Proton
install, no guessing. `strings` on the real implementation DLL
(`d3d12core.dll`, not the `d3d12.dll` stub — confirmed by finding
`VKD3D_CONFIG` references only in the former) shows the literal string
`descriptor_heap` alongside other known-real config flags
(`force_static_cbv`, `single_queue`, `no_upload_hvv`,
`skip_driver_workarounds`), plus a genuine runtime log format string,
`"VK_EXT_descriptor_heap enabled (%zu / %zu size, raw uav counter %s)."` —
this build recognizes and can enable the extension. So the negative result
stands: descriptor-heap exhaustion in vkd3d-proton's classic path, at least
as fixed by this config flag, is **not** what caused this specific
occurrence.

This build being from October 2026 also means it near-certainly already
includes vkd3d-proton 2.9's separate, earlier driver workaround for
concurrent-queue-submission/timeline-semaphore Xid 109 cases (which predates
the descriptor-heap work and fixed a different subset of occurrences in
other titles) — so that avenue is most likely already in play too, not a
fresh one to try.

## What's genuinely still untried, in priority order

Change exactly one variable at a time and reproduce (or fail to) before
trying the next, or a fix cannot be attributed.

1. **The driver-level fix at 620.70.06.** Raised to top priority on
   2026-11-09: an independent investigator (`Marukooh`, different hardware
   — RTX 5070 Ti, different title — Crimson Desert) reported 10+ clean
   minutes of a scenario that previously hung within minutes, on exactly
   this driver version. Still not confirmed-fixed even by its own reporter,
   and **still not available in this repo's current Nixpkgs pin** —
   re-checked directly on 2026-11-09 (`stable`, `production`, `latest` and
   even `bleeding_edge` all resolve to 595.71.05; `beta` is 595.45.04,
   `vulkan_beta` is 595.44.08 — both *older*, not newer). Blocked on
   upstream packaging, not on anything Helix controls. Revisit when the
   Nixpkgs pin is bumped far enough that a driver at or past 620.70.06
   appears in any `linuxPackages.nvidiaPackages.*` attribute; check its
   release notes for Xid 109 / bug 6017526 specifically rather than
   assuming a bump alone fixes it.
2. **A from-scratch native Vulkan/DX12 workload with zero Proton
   involvement.** Checked this Steam library on 2026-11-09 for a candidate:
   the one plausible native-Vulkan title installed, DOOM (2016, appid
   379720), ships only Windows PE executables here (`DOOMx64.exe`,
   `DOOMx64vk.exe` — confirmed with `file`, no native Linux binary present
   in this depot) despite id Software having shipped a native Linux Vulkan
   port historically; it runs under Proton like everything else in this
   library, not natively. No other installed title is both native Linux and
   a heavy enough Vulkan/DX12 consumer to be a useful test. Finding or
   acquiring a genuinely native, zero-Proton, descriptor-heap-heavy title
   remains the way to further separate "driver/GPU" from "translation
   layer," but nothing in the current library satisfies it.
3. **Accept that the trigger is broader than vkd3d-proton's descriptor-heap
   path** — already effectively confirmed, not just a possibility: the
   Fallout 4 occurrences (DXVK, not vkd3d-proton at all) and `Marukooh`'s
   GSP-reserved-VA-window forensics (independent hardware, independent
   title) both point at a GPU scheduler/context-switch defect reachable
   through more than one translation layer. No concrete next action beyond
   re-reading new reports on `#1097` periodically — but stop treating
   "descriptor heap exhaustion in vkd3d-proton" as the full explanation in
   any future note here.
4. **`open = false` (proprietary kernel modules) as a controlled A/B
   test.** Still lower priority: the likely root cause is now understood to
   sit below both translation layers, so switching kernel-module flavour
   doesn't obviously change anything about it either way, and confounds
   with items above if done first. `hardware/nvidia.nix`'s own comment
   ("NVIDIA lists this PCI family as requiring its open kernel modules")
   says this will likely just fail to produce a working graphical session
   rather than yield a usable comparison — confirm against current NVIDIA
   documentation before spending time on it, and expect to revert
   immediately either way.
5. **A different driver branch/version available in this Nixpkgs pin.**
   Lowest priority, and re-confirmed pointless as stated above: every
   available branch is either identical to the current 595.71.05
   (`production`, `latest`, `bleeding_edge`) or strictly older (`beta`
   595.45.04, `vulkan_beta` 595.44.08). There is no available branch that
   differs meaningfully from what's already pinned.
6. **`VKD3D_DISABLE_EXTENSIONS=VK_NV_raw_access_chains`**
   (`NVIDIA/open-gpu-kernel-modules#1409`) — a workaround for a *different*
   root cause reported on older (Turing) hardware, and specific to
   vkd3d-proton (would not apply to a DXVK/DX11 occurrence like Fallout
   4's). Likely not relevant to Blackwell, and it carries a known
   performance regression; only worth trying after everything above is
   exhausted.
7. **If Fallout 4's occurrences are ever revisited specifically**: do not
   reach for `VKD3D_CONFIG=descriptor_heap` — it is a vkd3d-proton/DX12
   flag and Fallout 4 never loads vkd3d-proton at all. Any targeted
   mitigation attempt there would need to be a DXVK-side option instead,
   and none is currently known to apply to this symptom; this is a gap, not
   a tried-and-failed lead.
